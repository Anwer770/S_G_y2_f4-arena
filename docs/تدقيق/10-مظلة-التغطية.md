## 3) العيب الأول: زرّا ↑/↓ لا يحرّكان شيئاً

`moveLookup` كانت:

```ts
[list[index], list[target]] = [list[target], list[index]];   // تبديل الموضع في المصفوفة
return { ...state, [kind]: sortAll(list) };                  // ثم إعادة الترتيب حسب order القديم!
```

`sortAll` تُرتّب حسب `order`، وقيم `order` لم تتغيّر ⇒ **التبديل يُلغى دائماً**، ولا يبقى من الاستدعاء إلا `updatedAt` وسطر تدقيق. الزرّان في «القوائم والثوابت» كانا يعملان شكلياً فقط.

الإصلاح: حذف العنصر من موضعه وإدراجه في الموضع الهدف، ثم الترقيم بحسب **الموضع**:

```ts
const [moved] = list.splice(index, 1);
list.splice(target, 0, moved);
return { ...state, [kind]: list.map((item, idx) => ({ ...item, order: idx + 1 })) };
```

**برهان قبل/بعد (تشغيل فعلي):** بإعادة الكود القديم مؤقتاً:

```
✗ L5 · الترتيب يحرّك العنصر فعلياً (أعلى/أسفل) ويُعيد ترقيماً متسلسلاً   ⇒ 38/39
tests/unit/lookupsLogic.test.ts (44 tests | 3 failed)
```

وبعد الإصلاح: `✔ L5` ⇒ **39/39** · الوحدة **44/44**.

## 4) العيب الثاني: بوابة خضراء زائفة

البوابة **L5** كانت تُسمّى «الترتيب يعمل ويُعيد ترقيماً متسلسلاً» وتفحص:

```js
m.categories[0].order === 1 && m.categories.every((i, idx) => i.order === idx + 1)
```

وهذه خاصية **صحيحة أصلاً** في أي حالة مرتّبة — تتحقّق حتى لو لم يتحرّك العنصر إطلاقاً. فمرّت البوابة خضراء على دالة لا تفعل شيئاً. صارت تقارن **الموضع الفعلي**: العنصر انتقل إلى موضع `n-1`، والعنصر الذي كان قبله صار بعده، ثم الحركة المعاكسة تُعيد الترتيب الأصلي حرفياً، والحدود تُعيد نفس الكائن.

> الدرس: البوابة يجب أن تقيس **الأثر**، لا أن تعيد صياغة **الحالة الابتدائية**.
