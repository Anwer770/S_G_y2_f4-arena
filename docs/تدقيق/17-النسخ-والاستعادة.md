> **الدفعة R51 · الإصدار 3.40.0 · 2026-11-07**

## لماذا هذه الدفعة

كل ما سبق يقيس **القراءة والكتابة**. هذه الدفعة تقيس **البقاء**: ماذا يحدث حين يضغط المستخدم
«استعادة» على ملف قديم؟ الخطأ هنا لا يُظهر رصيداً خاطئاً — بل يمحو سنة عمل، ثم يعلن «نجاح».
ولذلك بدأت الدفعة بالقياس لا بالكود: إدخال هذه الملفات في `coverage.include` **بلا اختبارات**
أنزل الإجمالي فوراً:

| المقياس         | قبل R51 | بعد الإدخال بلا اختبارات | بعد R51              |
| --------------- | ------- | ------------------------ | -------------------- |
| التعابير        | 99.91%  | **80.75%** (1313/1626)   | 99.93%               |
| الفروع          | 99.74%  | **82.33%** (876/1064)    | 99.81%               |
| الدوال          | 100%    | **94.11%** (320/340)     | 100%                 |
| الأسطر          | 100%    | **82.57%** (1142/1383)   | **100%** (1393/1393) |
| اختبارات الوحدة | 453     | 453                      | **493**              |

أي أن 236 سطراً من `backup.ts` — الملف الذي يستعيد بيانات المستخدم — لم يُقرأ منه سطر واحد في أي اختبار.

## العيوب المكتشفة (مُصلَحة كلها)

### 1. رقم إصدار كاذب في كل ملف نسخة احتياطية

```ts
// قبل
version: '3.2.0',            // جامد داخل تطبيق 3.39.0
// بعد
version: APP_VERSION,        // من `constants/appMeta`
```

كل ملف يُصدِّر المستخدم كان يحمل `3.2.0`. أثرُه عملي لا شكلي: أي فحص توافق مستقبلي على
`backup.version` كان سيقرأ رقماً عمره سبعة إصدارات، وأي دعم فني يطلب «رقم النسخة» سيحصل على رقم خاطئ.
(المفتاح `STORAGE_KEYS.UNIFIED_BACKUP` يحمل رقم إصدار ثانياً في اسمه — `_v2` — وذاك رقم **مخطط**، لا يُمسّ.)

### 2. «نسخة الطوارئ»: وعدٌ بلا قارئ

`clearAllData()` كان يكتب لقطة كاملة إلى `suite_unified_autobackup_v2`، ثم يمسح كل شيء، ويسجّل
«حفظ نسخة طوارئ مسبقة». **ولا قارئ لهذا المفتاح في التطبيق كله** — والـ`clearAllData` نفسه بلا أي
مستدعٍ. أي أن المسار الوحيد الذي يمحو بيانات المستخدم كان يكتب وعداً لا يمكن الوفاء به.

أُضيف القارئ، وأُغلق الطرفان:

```ts
export function loadEmergencyBackup(): UnifiedBackupState | null;
// + BackupService.restoreEmergencyBackup(): boolean
```

الاختبار لا يتحقق من «وجود الدالة»، بل ينشئ عميلاً معروفاً، ينفّذ `clearAllData`، **يتأكد أن السجل زال**،
ثم يستعيد فيجد العميل نفسه بالمعرّف نفسه. وهناك اختبار ثالث للقطة الغائبة أو التالفة: تحذير واحد،
`false`، **بلا انهيار** — لأنها قد تُستدعى على جهاز لم يُصفَّر قط.

### 3. الأخطر: سجل النظام كان يمحو سجل التدقيق

كان `STORAGE_KEYS.SYSTEM_AUDIT` و`AuditService.AUDIT_STORAGE_KEY` **المفتاح نفسه**
(`suite_unified_audit_v2`) — بشكلين مختلفين للبيانات:

```
سجل النظام   : { id, timestamp, module, action, recordId, details }
السجل المركزي: { id, timestamp, entity, recordId, action, userId, deviceId }
```

وبما أن كل استعادة تُسجَّل في سجل النظام، وملف النسخة يحتوي `systemLogs` أيضاً، فإن:

- أي استعادة تستبدل السجل المركزي بمصفوفة `AuditLog` ⇒ فئة `Customer/Create` تختفي؛
- وفي الاتجاه المعاكس، أي سطر مركزي يُقرأ في سجل النظام كـ`{ module: undefined }`.

قيس ذلك مباشرةً: بعد `auditService.log({entity:'Customer'})` ثم `logSystemAudit(...)` صار السطر الأول
`{ entity: undefined, action: 'استرجاع' }` مع بقاء سطر العميل — ثم بعد `restoreBackup` اختفى الاثنان
وبقي `['Restore']` وحده.

**الإصلاح:** مفتاح مستقل لسجل النظام، والقديم `legacyKeys` للقراءة فقط، مع مصفاة شكل:

```ts
const auditRepo = createCollectionRepository<AuditLog>({
  key: STORAGE_KEYS.SYSTEM_AUDIT_LOGS, // suite_system_audit_v2
  fallback: DEFAULT_SYSTEM_AUDIT,
  limit: 1000,
  legacyKeys: [STORAGE_KEYS.SYSTEM_AUDIT],
  isValidItem: (log) => typeof (log as AuditLog).module === 'string',
});
```

المصفاة ضرورية: البيانات القديمة **مختلطة فعلاً** على أجهزة المستخدمين؛ بلا مصفاة تنتقل الأسطر
المركزية إلى سجل النظام عند أول قراءة. النتيجة: لا فقدان لأي سطر، والأسطر المركزية القديمة تبقى
حيث يقرأها `AuditService` (لم يُحذف المفتاح القديم).

## قيد معروف (موثَّق لا مُصلَح)

**`fallbackOnEmpty` يعيد البذور عند الاستعادة.** إذا حذف المستخدم كل عملائه ثم استرجع نسخة تحتوي
مصفوفة فارغة، تُقرأ **بذور التطبيق** لا الفراغ — لأن عقد المستودعات (R45) يقول «الفراغ = لا بيانات ⇒
البذرة»، وهو عقد يشمل كل الوحدات ولا يخصّ الاستعادة وحدها. غيّره لصالح الاستعادة وحدها يحتاج
«وضع استعادة» في المستودع، وذاك قرار معماري خارج نطاق R51.

أثره الواقعي: أسوأ حالة هي عودة بذور بدل فراغ (لا فقدان بيانات إضافي). لذلك ثُبِّت السلوك في
اختبارين باسمه الصريح بدل تركه غير مقيس — ليُقرأ عند أي محاولة تغيير.

## المخاطر

- المفتاح القديم `suite_unified_audit_v2` ما زال يُقرأ كـlegacy: إن أُزيل يوماً، تُفقد أسطر سجل النظام
  المكتوبة قبل R51 على أجهزة المستخدمين. الإزالة تحتاج دورة ترحيل صريحة (كتابة ثم حذف) لا حذفاً مباشراً.
- التشفير يعتمد على Web Crypto: رمز PIN من أربعة أرقام مع PBKDF2 150,000 دورة يحمي من التخمين اليدوي،
  لا من هجوم خارجي على جهاز مُخترَق — وهذا حدّ التصميم لا عيب في التنفيذ.
